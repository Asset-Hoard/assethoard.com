How we built the AssetHoard MCP server

You're three hours into building a level. You need a barrel. You know you own at least four barrel packs, because you bought them in three different bundle sales and one of them was "a steal". Finding them means leaving the editor, opening a file browser, and digging through folders called Downloads (2).

Meanwhile there's an AI assistant sitting in your editor that can write a state machine in eight seconds but has no idea what's on your hard drive.

AssetHoard is a local-first desktop asset manager for indie game developers and digital artists, and version 0.2.3 fixes that with a built-in MCP server. This post covers how we built it, why it's locked down the way it is, and the things we've found it genuinely useful for.

What MCP is, briefly

The Model Context Protocol is an open standard for letting AI tools call other programs. A program exposes a set of named tools with typed arguments ("search", "export", "create_bundle"), and any MCP client (Claude Code, Cursor, VS Code, Windsurf, Claude Desktop) can discover and call them.

For an asset manager that's a natural fit. AssetHoard already knows every model, texture, sprite and sound you own, what's in which bundle, what it's tagged, and what each file depends on. MCP lets your assistant ask it.

The decisions that shaped it

Built into the app, not a separate program

The obvious shortcut would have been a little standalone server that opens AssetHoard's SQLite database and reads it directly. We didn't do that, for two reasons.

First, two programs writing to one SQLite file is how you end up with a corrupted library and a very bad afternoon. Second, the app would never find out about changes. You'd ask your assistant to tag forty rocks and the open window would keep showing them untagged until you restarted.

So the server runs inside AssetHoard itself, and the app has to be open for it to answer. That turned out to be a feature: every change the assistant makes shows up in the window straight away.

Living inside the app also means you stay in charge of it from the app:

  • Turn it on and off. One switch in Settings > MCP Server. It's off until you flip it, and a plug icon sits in the toolbar whenever it's running, so you're never guessing.
  • See what changed. When an assistant exports files or edits your library, AssetHoard shows a notification in the app saying what it did, and the settings page keeps a list of recent calls.
  • Decide how much the assistant can do. Out of the box it can only search, look and export. Changing your library needs "Allow write tools" switched on, and importing files pops up a prompt you have to approve. If you'd rather keep it read-only forever, just leave the write switch off.

One rule: MCP never touches the database directly

The MCP code lives in its own module, and it isn't allowed to call app commands or SQL. Everything goes through a small internal library API that sits underneath both the UI and the MCP server.

That sounds like bureaucracy, but it's what makes the write tools trustworthy. When an assistant moves an asset into a bundle, it runs exactly the same function as when you drag it there yourself. Same validation, same audit log, same undo entry. There's no second, slightly different code path quietly drifting out of sync with the real one.

It also makes adding a tool cheap. A new tool is a typed argument struct (whose doc comments become the descriptions the model reads) and a thin method that calls the library API. The interesting logic stays in one place and gets tested once.

Rust, rmcp and streamable HTTP

AssetHoard's backend is Rust, so we used rmcp, the official Rust SDK for MCP, with its streamable HTTP transport mounted on axum. Database work runs on blocking worker threads so a big search never stalls the app's async runtime, and each call is recorded in a recent-activity list you can watch in Settings.

We picked HTTP over stdio because the server lives inside a desktop app that's already running. Claude Code, Cursor, VS Code and Windsurf all connect to a local HTTP endpoint with a header, which is a one-line setup. Claude Desktop is the odd one out: it only launches stdio servers, so for now it connects through the mcp-remote bridge.

A fixed port, on purpose

The server listens on port 47823 by default. You can change it, but AssetHoard will never pick a different one on its own if that port is busy. Auto-switching sounds helpful until every client config you've written silently stops matching. Instead, a taken port shows up as an error with a readable message, and you choose what to do.

Making it safe to leave on

A local server that can read your files and write to your library deserves some paranoia. Here's what's in place:

  • Off by default. You turn it on in Settings > MCP Server.
  • Local only. It binds to 127.0.0.1, so nothing on your network or the internet can reach it.
  • Token required. Every request needs a bearer token: 48 random hex characters, compared in constant time. Regenerating it disconnects every client.
  • Browsers are refused. Any request with an Origin header is rejected, and the Host header must be a loopback address. Browsers always send Origin; CLI and IDE clients don't. This blocks DNS rebinding, where a malicious web page tries to talk to a server on your machine, and it's what the MCP spec asks local servers to do.
  • Write tools are a second opt-in. "Allow write tools" is a separate toggle, and it's checked on every call, so switching it off takes effect immediately, even for clients that are already connected.
  • No deleting your stuff. There are no tools for deleting assets or bundles. The only deletes are for categories nothing uses and projects that are already empty.
  • Exports never overwrite. If a file already exists at the destination, it's skipped and reported.
  • Imports ask first. When an assistant wants to import a folder, AssetHoard pops up a prompt with the path, file count, size and target bundle, and flashes the window. No answer within 60 seconds counts as no. If you trust your setup, "Import without asking" turns this off.
  • Everything is undoable. Writes go on the normal undo stack with an MCP: label, like MCP: Moved 1 asset into 'Rocks', and a toast tells you what changed. Ctrl+Z (Cmd+Z on a Mac) works exactly as it does for your own edits.

A plug icon appears in the toolbar whenever the server is running, so you always know it's on.

Small things that made a big difference

Search returns text, thumbnails are separate. Search results are ids, names, types, paths and tags, which keeps them small. If the assistant wants to actually look at something, it calls get_thumbnail and gets a preview image of at most 256 pixels. That means it can check that the "mossy rock" really is mossy before suggesting it, without flooding its context with every result's picture.

Dependencies come along. Exporting a model brings its textures. Exporting a Godot .tres brings the files it references, and Unreal assets bring theirs. Exporting a whole bundle keeps its folder layout. Assets inside zip archives or .unitypackage files are pulled out first.

Clickable links. Every asset, bundle and project the server returns includes an assethoard:// link. The assistant can hand you a link, you click it, and AssetHoard jumps to that item. We added the link scheme to the app specifically for this.

Errors the model can read. An unknown id, a bundle inside a package, or write tools being switched off all come back as plain error messages rather than protocol failures, so the assistant can explain what happened or try something else.

What you can do with it

Here's what this looks like in practice. These are the kinds of things you'd type into Claude Code, Cursor or similar with AssetHoard running.

Set dressing without leaving the editor

"Find three different barrel models and a wood texture that matches, and copy them into Assets/Props."

The assistant searches your library, looks at the thumbnails of the best few, picks a set and exports them, textures included. You keep building the level. This was the main use case we designed for, and it's the one in the demo video.

Search by what it looks like, not what it's called

"Do I have any mossy stone wall textures?"

Search works the same way as AssetHoard's search bar: by name with typo tolerance, and by meaning when semantic search is turned on. Since 0.2.3 that includes embedded audio metadata too, so "glass shatter" can find SFX_0472_FINAL.wav if that's what its description says.

Narrow it down like you would in the app

"Show me Godot UI sprites from my Kenney bundle."

Results can be filtered by file type, asset class, engine, tag, category or bundle. The assistant works out the bundle id itself and filters inside it.

Drop a whole tileset into a project

"Copy my 'Dungeon Tileset' bundle into the Godot project at C:/dev/crawler."

The bundle's sub-bundles become folders in the destination, so the structure you set up in AssetHoard carries over.

Tidy up the library (write tools on)

"Make a bundle called 'Rocks' under 'Environment', move every rock model into it and tag them 'nature'."

The assistant creates the bundle, searches, moves and tags. Each step appears live in the app and is its own undo entry. If it gets carried away and moves a boulder that was actually a potato, Ctrl+Z.

A slower but satisfying variation: "Find the untagged textures in my Downloads bundle, look at each one and suggest tags." Review the suggestions, say yes, and let it apply them.

Keep track of what a game uses

"Start a project called 'Crawler' and add the dungeon tileset and the footstep sounds to it."

Projects in AssetHoard only record references. Nothing moves, and an item can belong to several projects. Once a project is set up, you can ask questions like "list everything in Crawler and tell me which assets have no licence recorded", which is a much nicer way to find out before release than after.

Onboard a new pack

"Import C:/Users/me/Downloads/kenney_platformer-pack into my Kenney bundle, then categorise the new assets by type."

AssetHoard asks you to allow the import, runs it through the normal import queue with the usual progress notification, then the assistant categorises what came in. The whole import is one undo entry.

What's next

The main gap right now is Claude Desktop needing the mcp-remote bridge. A small native shim that lets it connect directly is on the list. We'd also like to hear what you end up using the server for, because the tool list was shaped by our own workflow and yours is probably weirder.

Try it

The MCP server is in AssetHoard 0.2.3 and later. Open Settings > MCP Server, switch it on, and paste the setup command into your client. The MCP docs cover each client, and the tool reference lists every tool and its arguments. AssetHoard is free to download during the open beta, so the only thing it'll cost you is finally finding out how many barrel packs you own.
